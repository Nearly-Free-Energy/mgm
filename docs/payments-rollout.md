# Payments rollout

Apply the complete migration chain, including `00065_payments_capability.sql` and `20261010202643_payments_integrity.sql`, before deploying the application. Existing community merchants remain separate accounts with community overrides; historical attempts keep their original account version. The integrity migration is safe to reapply.

Set the server-only `MGM_APP_URL` to the canonical HTTPS application origin. The payment return URL is that origin plus `/payment/callback`. The former `NEXT_PUBLIC_APP_URL` and `NEXT_PUBLIC_PAYMENT_CALLBACK_URL` are no longer read (see `docs/setup.md`, "Upgrading from v0.0.1 or v0.0.2"). Configure a strong random `PAYMENTS_WORKER_SECRET` in the server environment. Store the same secret in Supabase Vault as `payments_worker_secret`, and the HTTPS `/api/payments/reconcile-worker` URL as `payments_worker_url`, using secure administrative tooling. Never commit these values. The migration schedules `mgm-payments-reconcile` every five minutes; without Vault configuration its database runner reports a configuration error, and without the application secret the endpoint fails closed. Monitor cron run details and application worker responses. Failed notifications back off and eventually become `dead_letter`; investigate these records rather than starting another checkout blindly.

In Organization → Payment accounts, configure and test a Pesapal sandbox merchant first. Enable Payments and Pesapal in plugin settings. A community inherits the organization default unless its Payment accounts page selects an override. Failed credential tests preserve the active configuration. No automatic payment email is sent; use the stable MGM payment link in an invoice or copy it manually. Managers copy each bill's link from its period's payment links page (`/microgrids/<id>/billing/<period id>/send`, Payment links on the period), which shows links only while the community's payment readiness is ready or sandbox, and says why there are none otherwise. That page sends nothing: the manager shares each link. Each link lets whoever holds it start a checkout for that bill, so send it only to the bill's tenant.

Opening a payment link (a GET on `/api/billing-line-items/<id>/pay`) starts a checkout for the bill, or reuses the one already open, and chat and email apps fetch the links people paste to build a preview. Because checkout reuses an open attempt while the bill is unchanged (`ensureCheckout`), such a preview fetch starts at most one checkout for the bill's current total, which the tenant's own visit then reuses. That holds only while the bill's total stays the same. A change to the total (a draft correction, say) flags every open checkout for the bill for reconciliation, the one a preview started included, and a bill with a payment needing reconciliation refuses new checkouts (`409 payments_needs_reconciliation`). Refreshing the attempt's status does not clear it: the tenant's visit gets no checkout until a manager reconciles it from the bill's payment history, and reconciling settles the bill, which needs its receipts plus any amount recorded from outside MGM to equal the new total. A checkout the tenant opened and abandoned does the same; a preview does it without anyone opening the link. So share a bill's link once its total is final. A follow-up (#219) will make the GET show a page whose button starts the checkout.

While Payments is off, the period's Payments tab is still listed and opens with the notice that Payments are disabled, and its Refresh status and both reconciliations stay available, as they were in the legacy period row's Payment history dialog (deleted in #201): their routes accept them while Payments is off, since verification and reconciliation of attempts already submitted are kept (the billing parity table's `payments-while-off` row, `src/lib/billing/parity.ts`). The signals still report each period with payments held for reconciliation (`payments.reconcile`), and no longer report recent failures (`payments.failed`) or checkouts that never reached Pesapal (`payments.not-submitted`), since no customer can pay online then. New checkouts are still refused.

While Payments is on, Today and the signals tray report three things about payments. `payments.reconcile` reports each period with attempts held for reconciliation: critical when any of them reached Pesapal (it has a Pesapal tracking id or a receipt), so money may have moved, and a warning ("checkouts … need reconciliation") when none did, as for a checkout flagged by a draft total correction before anyone opened its link. `payments.failed` reports each period with failures in the last seven days on bills still unpaid, as a warning; it leaves out checkouts replaced by a newer one and checkouts Pesapal never accepted, since the customer is simply asked to try again. `payments.not-submitted` reports, as a warning, each community where three or more checkouts never reached Pesapal in the last 24 hours, linking to the community's payment setup: one such failure is a passing provider error, several in a day usually mean the payment account (its keys, its IPN registration or Pesapal itself) needs checking. If it cannot read every such checkout at once (more than 500 in the window), it is listed as not checked rather than undercounting.

Before enabling live payments, have the operator perform a sandbox checkout and confirm all of the following:

- The return page (`/payment/callback`) says the status was checked only after a server-side lookup, never from the redirect parameters, and the bill, receipt, and audit event agree. The provider should bring the tenant back with a `GET`: a `POST` shows the plain "not confirmed yet" page and checks nothing.
- The return page names the operator from the community's invoice branding: the trade name, else the organization's name, with the community beneath, and the WhatsApp contact the bill shows. A PNG or JPEG logo of 6 KB or less, uploaded for that community, appears too; a larger logo, or an SVG, leaves the name alone. The page waits at most 2 seconds for the branding: past that it answers without the logo, or without any branding if the names were not read in time.
- Repeated IPNs, repeated clicks, and worker delivery do not duplicate accounting or create another outstanding checkout.
- A draft total correction flags any old payment for reconciliation. Payment history shows the current total, received amount, and difference: in the period row's Payment history dialog, and on the period's Payments tab (`/microgrids/<id>/billing/<period id>/payments`, one bill with `?bill=<bill id>`).
- Plugin disablement blocks new checkout while keeping history and verification available. Manual payment recording remains independent.
- A verified reversal updates accounting. Any external reconciliation records the actual signed collection/refund amount, reference, and notes, and asks for the tenant's name typed; MGM does not execute refunds.
- Notifications recover after a worker interruption, and persistent failures remain visible for investigation.

Local verification uses synthetic records and rolls back all rehearsal writes. Run `psql "$DB_URL" -v ON_ERROR_STOP=1 -f supabase/scripts/rehearse-payments.sql` against a scratch database. This exercises reservation, settlement rollback, duplicate events, reversal, correction, external settlement, organization isolation, and scheduler presence. It does not replace the operator's Pesapal sandbox transaction or deployment configuration checks.
