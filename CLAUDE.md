# CLAUDE.md — MGM (Microgrid Manager)

Tool-specific config for Claude Code. MGM is a microgrid operating system built on [Cordis](https://github.com/cordiverse/cordis) plugins. Everything an agent or contributor needs lives in this repository.

- `CONTRIBUTING.md` — contributor setup, sign-off, signed commits, and the required checks.
- `docs/cordis-runtime.md` — how plugins, request scopes, and the plugin gate fit together.
- `docs/entity-model.md` — the data model and the reasoning behind it.
- `docs/adr/ADR-006-gui-contract-v0.md` — the GUI contract (v0, experimental): what capabilities contribute, what interfaces render, and the import boundaries between them.

```bash

# Tests

# Browser smoke at 360 px (local Supabase and `npm run build` first; docs/setup.md)
npm run test:e2e

# Build (standalone for Docker)
npm run build

# Generate TypeScript types from local Supabase (requires supabase start)
npm run db:types

# Print the linked project's types, to compare with (never commit them as database.gen.ts)
npm run db:types:linked

# Check that database.gen.ts is in sync with the schema (run by husky pre-commit)
npm run db:types:check
```

**Codegen workflow:** After any schema migration (`supabase/migrations/*.sql`), run `npm run db:types` to regenerate `src/lib/types/database.gen.ts`. A husky pre-commit hook (`npm run db:types:check`) blocks commits when the generated file is out of date, and the `Test` gate regenerates it from a database built from the migrations alone and fails on any difference. The pinned Supabase CLI (3.x, from `package-lock.json`) prints the types unformatted, so the `db:types` scripts (`scripts/db-types.sh`) pass them through the pinned prettier (`--no-semi`, the style postgres-meta formats with), and write the file only when every stage succeeds; regenerate through those scripts, not with `npx supabase gen types` alone, or the file will not match. Regenerate from a local database built from this branch's migrations (`supabase db reset`). `npm run db:types:linked` only prints the linked project's types (`gen types --remote`), for comparison: the CLI reads that database directly only when a database password is available and otherwise asks Supabase's hosted generator, and a project's schema can drift from the migrations (production has), so those types are not the committed file's.

### Running RLS Tests

RLS tests (`src/lib/supabase/__tests__/rls.test.ts`) require:

1. **Local Supabase CLI running**, with Supabase CLI 3.4 or later (`npx supabase` runs the pinned one; `docs/setup.md`, "Upgrading to Supabase CLI 3") — `MGM_ALLOW_DEV_CREDENTIAL_KEY=1 supabase start` (do NOT run against cloud). The variable gives a new local database a throwaway credential encryption key; without it the migrations stop at `00018` (`docs/runbooks/dek.md`).
2. **`SUPABASE_JWT_SECRET` in `.env.local`** — retrieve with `supabase status -o env | grep '^JWT_SECRET='`
3. **Seed loaded** — run `MGM_ALLOW_DEV_CREDENTIAL_KEY=1 supabase db reset` once after `supabase start`

Set `SKIP_RLS_TESTS=1` to bypass RLS tests **locally**, when you have no local Supabase running. **The `Test` gate no longer sets it** — since #324 CI starts its own Supabase and runs these suites, so a change that passes only because you skipped them locally will fail on the PR.
The DEK bootstrap suite (`src/lib/supabase/__tests__/dek-bootstrap.test.ts`) resets the local database twice, so it runs only with `RUN_DEK_BOOTSTRAP_TEST=1`; otherwise `npm test` reports it as skipped. CI runs it in its own last step (§ "Required Merge Controls").
Missing env vars without `SKIP_RLS_TESTS=1` fail loudly — this is intentional.

See `docs/setup.md § "RLS Tests"` for full instructions.

**Stop the local Supabase you started.** Each `supabase start` runs about ten containers and takes roughly a gigabyte of memory, and a stack started for one task under its own `project_id` (such as `mgm-email` or `mgm-tenant`) keeps running after the task ends until Docker runs out of memory. When you are done with a stack you started, run `supabase stop` from the directory you started it in, or `supabase stop --project-id <id>` from anywhere; both keep its database for the next `supabase start`. Leave the main `mgm` stack, and any stack another running session is using, alone.

## Stack

- **Framework:** Next.js 16 (App Router)
- **Plugin runtime:** Cordis 4 (`src/lib/runtime/`, see `docs/cordis-runtime.md`)
- **Auth + DB:** Supabase (Postgres + Auth + RLS)
- **Hosting:** Vercel (free tier)
- **Styling:** Tailwind CSS + shadcn/ui
- **Testing:** Vitest
- **OpenEMS Integration:** Server-side adapter (`src/lib/openems/`), exposed to billing through the metering provider registry
- **Payments:** Pesapal, as a provider plugin of the Payments capability

## Key Conventions

- **Server-side only** for OpenEMS — all B2B calls go through `src/app/api/openems/*` routes
- **No `NEXT_PUBLIC_`** on OpenEMS credentials — they're server-side env vars
- **RLS everywhere** — new tables need Row Level Security policies
- **Adapter pattern** — billing logic doesn't import OpenEMS-specific types. `DeviceDataAdapter` interface in `src/lib/adapters/types.ts` (renamed from `MeterDataAdapter` in legacy#51)
- **Codegen types** — import entity types from `@/lib/types/domain`, never from `database.gen.ts` directly. Run `npm run db:types` after schema changes.
- **Role constants** — import `SUPER_ADMIN`, `ORG_MANAGER`, `TENANT`, `SCOPE_ORG`, `SCOPE_TENANT` from `@/lib/roles` instead of spelling out string literals. Three roles ship: the staff roles `super_admin` and `org_manager`, both `scope_type='org'`, and `tenant` (RFC mgm#197), `scope_type='tenant'` with `scope_id` a `tenants.id`, one row per unit a person rents, in any number of organizations. **"Staff" is not a role** (`user_role` has no `staff` value): it means holding a `user_roles` row whose role is not `tenant`, now; `staff_access_accounts` is the history of who ever did. `src/lib/roles.ts` holds the definition. **A tenant row is not staff, so "has a role row" does not mean "is staff"**: a staff check filters on the staff roles or on `scope_type='org'`, never on `roles.length` or `EXISTS (user_roles …)` alone. In application code that is `staffRoles` / `rolesIncludeStaff` / `rolesAreTenantOnly` (`@/lib/auth/access`), which count every role but `tenant` as staff, as `staff_access_accounts` does; the invite route, the Users page, the (gui) layout and the host's staff entry points that check no single organization (`installationRequest`, `visibleOrganizations`, `resolveSegments`, `dispatchView`, `buildManifest`, `buildActionCatalog`) read them. `DELETE /api/users/[id]` and resend-invite filter `role <> 'tenant'` inline in the same way. Entity deletion's actor role (`resolveActorRole`) and the host's per-organization checks (`surfaceRequest`, `pluginGate`, through `rolesCanAccessOrg`) allow-list `super_admin` and `org_manager` instead. A staff gate gets a test that a tenant-only user is refused. Filtering on the scope type is enough only while `user_roles_role_scope_type_consistent` pins each role to its scope type (`20261118100100`). Tenant rows are granted and removed by `fn_tenant_access_grant` / `fn_tenant_access_revoke` from the tenant record, never by the Users page, invitations or `fn_change_user_role`, which reject `tenant`. The Users page leaves them in place both ways: `DELETE /api/users/[id]` removes only a person's staff rows, and an invitation to an address whose only rows are tenant rows is a role change: a super admin's invitation gives the role through `fn_change_user_role`, whose DELETE takes only org-scoped rows, so the tenant rows stay, and anyone else gets the `other_access` answer any account with access gets, with nothing written, so no answer tells an org manager that the address is a tenant's. The invite route never calls `fn_finalize_user_invitation` for an account that holds any `user_roles` row. Tenant access does not depend on staff rows: `fn_tenant_access_grant` gives units to staff and non-staff alike, so a person may hold both. Once a person's staff rows are removed, by `DELETE /api/users/[id]` or any other path, they are exactly a tenant who never had one: tenant rows untouched, given further units like any tenant, left off the Users page, sent to tenant pages by the (gui) layout like a tenant-only person (§ "RLS helper functions"); the layout redirect is navigation, not an access check, since a layout does not run on every render (`docs/cordis-runtime.md`). The `ems_operator` role value and the `microgrid` scope type still exist in the enums and always will — `ALTER TYPE … ADD VALUE` cannot be undone — but **no role ships on them and no access check grants anything for them** (#321 deleted the rows and repointed the predicate). Where staff are told apart from tenants, an `ems_operator` row counts as staff (`staffRoles`, `staff_access_accounts`, `fn_list_visible_users`), so a stray one never reads as a tenant. The enums are deliberately wider than the constants; do not add constants back for enum values that carry no model. A user may still hold several role rows at once — `user_roles` is `UNIQUE (user_id, role, scope_type, scope_id)`, not one row per user. **Code that assumes one row per user is a bug** (see `fn_list_visible_users`); that constraint outlived the role that motivated it, and `fn_change_user_role` deleting rows it was not asked about is the data-loss path it exists to prevent.
- **Microgrid SELECT lists** — avoid `.select('*')` on `microgrids`; enumerate columns via `MICROGRID_PUBLIC_COLUMNS` (`src/lib/types/microgrid-columns.ts`) so new sensitive additions don't silently leak. Enforced by `src/lib/__tests__/no-microgrid-star-select.test.ts`.
- **Session checks before privilege** — middleware verifies only the access token's signature and expiry (`supabase.auth.getClaims()`); it does not ask Supabase Auth whether the session still exists, so a session signed out on another device passes it until the token expires (up to an hour). Reading through RLS with the user's own client needs nothing more, since the token holder could make the same query directly. Anything beyond that — the service-role client, decrypting a stored credential, a service-role helper — must first pass a `getUser()`-backed check on its own code path: `supabase.auth.getUser()`, a `currentUser*` helper from `@/lib/auth/access`, or a composer that runs `authorizeOrganization` (`composeBilling`, `composeCommunityManagement`, `composeMetering`, `composePayments`; not `composeBillingReview` or `composePaymentsPublic`) or `authorizeTenant` (`composeTenantApp`). A check in a layout does not count, because App Router renders layouts alongside the page and skips them on client-side navigation. `src/lib/__tests__/service-role-session-check.test.ts` follows the whole import graph of `src/`, plus the metering provider registry and the GUI surface (`mgmSurface`), which code reaches by name rather than by import. It lists every `src/app` file that reaches the service role or a stored credential, directly or indirectly, with its reason, and says for each module outside `src/app` which exports pass that reach on to an importer. A new path fails it until it is listed. If middleware goes back to calling `getUser()`, this rule stops being the only defence but stays correct. **Pre-session exceptions:** sign-in by email (RFC #186) runs before any session exists, so `/api/auth/sign-in-link` reaches the service role with no session check, listed as `public` there with its reason. It may only claim the rate limit, look up a person with an MGM role and call `generateLink`; it decrypts no stored credential, and sign-in mail goes only through the deployment's sender (`MGM_SMTP_URL`), never an organization's. `GET /api/auth/discovery` (#271), what `mgm login --url` asks before anyone is signed in, is the second: it reads only `client_id` and `kind` from `mgm_clients` and answers values that are already public; it is listed `unreleased` until the CLI ships, then `public`.
- **Cordis runtime** — see `docs/cordis-runtime.md`. One long-lived root context per process (`src/lib/runtime/root.ts`) holds the catalog, the plugin gate, the GUI surface, and the provider registries; each request runs in an isolated scope opened by a `compose*` function. Its rules:
  - A new **write** route of a non-core plugin must refuse while that plugin is disabled. It calls `gateRoute()` or `checkGate()` with the plugin that owns it in `src/lib/plugins/bundled.ts` and returns the blocked response, or it calls a composer that refuses that plugin itself: `composeCommunityManagement`, `composeMetering`, `composeTenantApp`, or `composeBilling` without `readOnly`. `composeBillingReview`, `composeBilling` with `readOnly`, and the payments composers do not count. `src/lib/runtime/__tests__/route-surface.test.ts` fails the build otherwise — its `COMPOSERS` map is the list of composers that count — and exemptions need a written reason in `UNGATED_WRITES` (`src/lib/runtime/__tests__/route-rules.ts`, which that test and `gui-surface.test.ts` both read); an exempt route that reaches the Payments capability needs a `PaymentExemption` naming the one method it calls, and its route file may not consult the plugin gate (`gateRoute`, `checkGate`, the plugin-state helpers), since the GUI host keeps its `whilePluginOff` actions enabled on the exemption's word.
  - A **write** route on a released path is a described action or has a written reason (RFC #259 § 3). Every `POST`, `PUT`, `PATCH` or `DELETE` handler under `src/app/api` whose path is released is named, by its method and path, by an action a plugin contributes to the GUI surface, or has an entry in `UNDESCRIBED_WRITES` (`src/lib/runtime/__tests__/route-rules.ts`), keyed as `UNGATED_WRITES` is. An entry is `permanent`, with the reason the route is not a person's action (no person sends it, or it writes nothing: a `POST` that only reads is not an action) and what would make that wrong (a "Wrong once …" clause, which the test requires; name a condition that is false today, or it warns nobody), or `not-yet-described`, naming the issue in `DESCRIBING_ISSUES` (same file) that will describe it, which must list the route's owner. Core plugins are held to it too: the gate rule above skips them, this one does not. `src/lib/runtime/__tests__/described-writes.test.ts` reads the actions from the runtime root's surface snapshot and fails for a released write handler in neither place, for an entry an action now names or whose handler is gone, and for an issue no entry names, so the pull request that describes a route removes its entry, and the one that removes an issue's last entry removes the issue. Release is decided per path, whatever the method (`isReleasedRoute` in `src/lib/mgm/released-routes.ts`), so every write method on a released path counts. An entry may name a route that is not released yet; a route written before its release needs its action or its entry by the commit that releases it. The test checks an entry's issue against the route's owner, not whether the route is new, so review is what keeps a new route from being parked under an open issue: every entry is a change to a code-owned file. An action is never a `GET` (`ActionDef["method"]` in `src/lib/gui/surface.ts`), so a `GET` that writes is outside this rule. If actions gain `GET`, a route file outside `src/app/api` starts writing, or release starts being decided per method, revisit the test and this rule.
  - A plugin is on for an organization that has no `mgm_plugins` row for it, so existing organizations need no backfill, **except a plugin whose catalog entry says `defaultEnabled: false`, as the tenant app's and the operations plugin's do**: it stays off until an operator turns it on for that organization, because a missing row must not give every organization's tenants an app nobody switched on (RFC mgm#197 § 3), nor put every organization's investigations on one shared evidence budget nobody opted into (#133). Two lists answer the question. `mgm_plugin_enabled_for_org` names the default-off plugins in SQL, and the gate, the GUI host and the composers read it; Settings → Plugins reads `defaultEnabled` (`resolvePluginStatuses`, and `validatePluginToggle` for dependents). Change a plugin's default on both sides in one commit, the SQL side in a new migration: `src/lib/plugins/__tests__/default-off-plugins.test.ts` reads the newest migration's list and fails while the two differ, and also while a bundled plugin is missing from the plugin-name CHECKs or `fn_mgm_set_plugin_enabled`. `mgm_plugin_enabled_for_org` answers any signed-in caller about any organization, tenant-only accounts included, which `composeTenantApp` and the tenant app's usage source (its metering gate) rely on to ask with a tenant's own token, and `fn_tenant_shared_meter_days`, which calls it as its definer with the tenant's `auth.uid()`; it discloses only an organization's plugin on/off state for an id the caller already has. If it gains an access check, let a tenant through for their own unit's organization first, or every tenant is refused. `composeTenantApp`'s scope carries no organization access (only the unit's organization and the caller's tenant rows), so it is opened with `audience: "tenant"`: every capability plugin that trusts `organizationId` or `roles` (community-management, metering, billing, payments, billing-review) calls `requireOrganizationAudience` first in `apply` and refuses it, and the tenant-app plugin loads into no other audience. A new such plugin calls it too.
  - A capability plugin that `provide`s a new service name must add it to `REQUEST_SERVICES` in `src/lib/runtime/scope.ts`, or concurrent requests collide (Cordis rejects the second provide).
  - A new metering source or payment provider is a platform plugin that registers into `meteringProviders` / `paymentProviderRegistry`; billing and routes do not change.
  - A capability's GUI integration is a surface contribution, registered on the root by a **platform** plugin (`ctx.effect(() => ctx.mgmSurface.contribute(…))`), never by the request-scoped capability plugin. `mgmSurface` is a root service and stays out of `REQUEST_SERVICES`: a request scope that isolated it would see no contributions. `contribute()` and `install()` stay deterministic, with no environment, network or database reads, so the `Test` gate's root build (`runtime.test.ts`) refuses exactly what production would. A refused contribution stops the runtime, payments included. The contribution check refuses the assistant mark (`agent: "read"`) on every view and watcher of billing, payments, Pesapal and the tenant app, on tenant views and views reached from configure or system navigation, on views that take signals, on views that declare a key prefix (`declares.prefixes`), and on views whose path names a tenant, device, rate schedule, billing period, line item or payment attempt; every mark, wherever allowed, needs the view's or watcher's entry in the code-owned list `src/lib/gui/assistant-reads.ts`, added in its own pull request with the mark and reviewed against ADR-007 (PR #261) decisions 6 and 7. What a contribution names (routes, body schemas, links, the capability methods its modules use) is checked by `src/lib/gui/__tests__/gui-surface.test.ts`; a new contributing plugin lists the module that exports its contribution in that test's `SURFACE_MODULES`, as an `@/` specifier. While a plugin is off for the organization, the host shows its actions disabled and refuses to prepare them, lists its sections and leaves out its tabs and tiles; an action stays enabled and preparable only when it declares `whilePluginOff: "enabled"`, which `gui-surface.test.ts` allows only where its `METHOD /api/route` is a `PaymentExemption` in `UNGATED_WRITES`, and a tab or tile is listed only with `attach.whilePluginOff: "listed"`, allowed only on a Payments or Pesapal view while every Payments method in `LOADER_READS` runs while off. The gate is still asked, and only its 409 is passed over, never its 503. Remove the field when the exemption goes. Every action declares `repeat` (ADR-006 decision 11): a `safe` one gets a case in its plugin's module under `src/lib/gui/__tests__/repeat/`, which `repeat.db.test.ts` sends twice to its route against a database; a billing, payments or Pesapal action is never `unsafe` unless `REPEAT_KEY_PENDING` there names the issue building its repeat key; nothing is `keyed` until a route takes a repeat key (#259). A view about a tenant's own unit is `scope: "tenant"` (RFC mgm#197): no path segments, no `attach`, never `agent: "read"` (#133's data boundary), reached only from an `audience: "tenant"` nav entry; the host picks the unit among the caller's tenant rows, reads no organization, asks no gate and offers no action, so its loader must authorize through `composeTenantApp`. A loader may read an organization's records on the server after `composeTenantApp`, to compute the unit's own figures, only if it asks the gate of each plugin whose records it reads, and none of those records may reach the model; the usage views and the home's month so far do this (`usage-source.ts` asks the metering gate before each uncached read). `contribution-schema.ts` refuses the rest; if tenant views ever carry actions, put an organization's record into a model, or read one before `composeTenantApp` or without asking the gate of each plugin whose records they read, revisit `dispatchTenantView` (`src/lib/gui/host/server/view.ts`), and keep its comment and this rule in agreement. A nav entry with no `audience` is `staff`, hidden from a person whose rows are all tenant rows; tenant entries follow the plugin state of the caller's own units' organizations, never that of the organization the manifest is built for.
  - A new signed-in **page** goes into its plugin's `pages` in `src/lib/plugins/bundled.ts`, with the entity kind of each bracketed segment, and either in the same commit as its `released-routes.ts` entry or, while it is unreleased, in `UNRELEASED_PAGES` in `src/lib/plugins/__tests__/catalog-pages.test.ts` with a reason. That test fails otherwise. It also pins each page's owner in `PAGE_OWNERS` and each segment's kind in `SEGMENT_KINDS`, so a new page or bracket name goes there too; pages outside any plugin (sign-in, first-run setup) are listed in its `HOST_PAGES` with a reason. A `page.tsx` under `src/app/(gui)` makes `await keepTenantOnlyToTenantPages()` its first call, before it reads anything: it sends a person whose rows are all tenant rows from any page a tenant view does not serve, which the layout cannot do alone, since a client-side navigation skips it. `src/app/(gui)/__tests__/tenant-only-pages.test.tsx` finds every page file and fails otherwise.

### Entity model (post-legacy#50)

`legacy#N` is an issue or ticket number in the upstream project's tracker from before the fork, kept where the history matters. It is not an MGM issue; MGM's own numbers are written `#N`.

The schema follows Org → Community → Microgrid → Edge → Device plus a parallel Tenant → tenant_devices join. Two staff roles ship (`super_admin`, `org_manager`) and one tenant role (`tenant`, RFC mgm#197); `microgrid_manager` / `community_admin` / `region_admin` are future extensions via enum addition. Tenant access is a `user_roles` tenant row; `tenant_users` was dropped by `20261118100100`. See `docs/entity-model.md` for the full rationale.

**Schema change notes:**
- `microgrids.location` TEXT was **dropped** — use the structured address columns instead (`address_city`, `address_region`, `address_country`, `lat`, `lng`). Downstream pages that read `location` were expected to fail at type-check until legacy#51 landed.
- Old `meters` table renamed to `devices` with a `device_type` enum; old `tenants` → `households` + `household_devices` many-to-many, renamed to `tenants` + `tenant_devices` by `20261116230000` (`docs/entity-model.md` § "Naming").
- `user_roles` moved from `(user_id, org_id, role)` to `(user_id, role, scope_type, scope_id)`; the old `system_admin` / `org_admin` role names are gone.

### RLS helper functions (migrations 00002_rls.sql and 20261118100100)

**Five** `SECURITY DEFINER STABLE` helpers, pinned to `search_path = public, pg_temp`, owned by `postgres`. All policies chain through these — do not inline JOIN chains in `USING` clauses. The deprecated alias `user_can_configure_ems` (00053) was dropped by `20261114223000`. The first three are staff access; the last two (RFC mgm#197) are a tenant's access to their own unit.

| Helper | Contract |
|---|---|
| `is_super_admin() -> BOOLEAN` | True iff `auth.uid()` has any `user_roles` row with `role='super_admin'`. |
| `user_can_access_org(_org_id UUID) -> BOOLEAN` | True iff `is_super_admin()` OR exists a `user_roles` row with `role='org_manager' AND scope_type='org' AND scope_id=_org_id`. |
| `user_can_access_microgrid(_microgrid_id UUID) -> BOOLEAN` | True iff `user_can_access_org(<microgrid's org_id>)` — resolves via `microgrids → communities → org_id`. |
| `user_can_access_tenant(_tenant_id UUID) -> BOOLEAN` | True iff `auth.uid()` has a `user_roles` row with `role='tenant' AND scope_type='tenant' AND scope_id=_tenant_id`. **Does not include `is_super_admin()`**, on purpose: staff already read tenants through the `FOR ALL` policies, and a helper that only ever says "this is your own unit" has nothing to widen. Do not add staff to it. |
| `user_is_tenant_of_device(_device_id UUID) -> BOOLEAN` | True iff `auth.uid()` holds a tenant row for a tenant that any `tenant_devices` row links to the device, whatever its effective dates. Reads `tenant_devices` as the definer, so the `devices` policy does not depend on the RLS of `tenant_devices`. Effective dates are the tenant app's job (RFC mgm#197 § 5); do not write a policy on per-day data (`meter_readings`, billing) with this helper, or a former tenant would see the meter after moving out. So a former tenant keeps reading the `devices` row of a meter that moved away, on purpose: the tenant app shows the days before the move from it (`20261118140000` kept this and put the reason on the function). That is safe only while every `devices` column may be read by a former tenant of the meter; the column pin below covers it. Also excludes staff. |

RLS policies are written with `FOR ALL` (not split per-verb) to match the existing pattern. **The one exception is the tenant policies** (`20261118100100`): `FOR SELECT … TO authenticated` on `tenants` ("Tenants can read their own tenant"), `tenant_devices` ("… their own meter assignments") and `devices` ("… their own devices"), named separately so Postgres ORs them with the staff `FOR ALL` policies and no staff policy is edited. They stay `FOR SELECT`: the SECURITY INVOKER write functions (`fn_create_tenant`, `fn_replace_tenant_device`, `fn_entity_delete_*`) are closed to tenants only because no tenant policy allows a write.

**The clients tables are the other exception** (`20261126090000`, ADR-008 decision 2). `mgm_clients` (the clients that are not a browser which an installation accepts) and `mgm_client_approvals` (a person's approval of one client sign-in, written by MGM's server as the service role) have policies `TO supabase_auth_admin` only: `FOR SELECT` on both and `FOR UPDATE` on the approvals, with column grants to match. Supabase Auth runs `fn_auth_access_token_hook`, which is SECURITY INVOKER, as that role, and it does not bypass RLS. `anon` and `authenticated` hold no privilege and no policy on either table, and the assistant's role (#274) gets none either. If the hook reads or writes another column, grant it in a new migration. What the role lacks stops every client sign-in and no browser sign-in: a missing column grant raises permission denied, which Supabase Auth answers with 500 "Error running hook URI"; a missing policy raises nothing, and the hook finds no row and refuses with its own 403. The hook refuses an `agent` client until #274 gives it its own role. `src/lib/supabase/__tests__/auth_access_token_hook_clients.test.ts` pins the grants and policies and signs a client in through Supabase Auth. When the hook is turned off to change it, the OAuth server goes off first and back on last (`docs/setup.md`).

**No tenant policy on `microgrids`, `edges`, `communities` or `organizations`.** A policy is row-level, so a tenant holding a JWT could `select=*` every column through PostgREST, and `microgrids` carries the EMS address, usernames and encrypted credentials. `MICROGRID_PUBLIC_COLUMNS` is an app-side projection and does not protect that path. The tenant's microgrid name, time zone and currency come from `fn_tenant_home(_tenant_id)`, a `SECURITY DEFINER` function that checks `user_can_access_tenant` and returns those columns only; add a column there only if a tenant may see it. If a tenant policy is ever added on one of these tables, revisit this rule, `fn_tenant_home`, the `tenant` and `device` cases of `resolveTargetOrganization` (`src/lib/runtime/gate.ts`) and the `microgrid_shared_devices` view, which today return nothing to a tenant because the edges and microgrids are invisible to them.

The tenant app's usage reads (`src/lib/tenant-app/infrastructure/usage-source.ts`) read the edges of the tenant's meters and build the microgrid's metering provider, which decrypts the stored OpenEMS credential, on the service role, after `composeTenantApp`, for the microgrid `fn_tenant_home` returns and the device rows the tenant's own client returns; the edges read is filtered to that microgrid, so a meter linked to the unit on another microgrid's edge is never read. Nothing those reads return reaches the tenant but the unit's own per-day and per-hour sums. If that source ever takes an id from the request or runs before `composeTenantApp`, revisit it with this rule. Only the unit's primary consumption meter is its use (`USAGE_METER_ROLE` in `src/lib/tenant-app/types.ts`). Which days a meter of the unit is also the primary of another unit, on any microgrid, so that it is labelled as shared on those days (D12 on #217), the source asks with the tenant's own client through `fn_tenant_shared_meter_days(_tenant_id, _from_date, _to_date)`, never on the service role. It is `SECURITY DEFINER` and refuses (42501) anyone `user_can_access_tenant` does not answer for, the service role included, and any unit whose organization has the tenant app off; it re-reads the unit's own primary consumption-meter links itself, counts every other unit that holds the meter as primary, whatever its microgrid (billing bills each, mgm#228), answers no day after UTC's date + 2, and returns device ids and date spans, merged per meter and cut to the unit's own links and the range, never which unit or how many. A tenant can call it directly through PostgREST, so every row it returns is the tenant's to read whatever the views show: a new column, a wider range or a count is a disclosure to the tenant. Its role and device type are `USAGE_METER_ROLE` and `USAGE_DEVICE_TYPE` written in SQL; change them together, the function in a new migration. If it ever returns a tenant id or a count, takes device ids or a microgrid from its caller, answers past that bound, stops counting a unit that holds the meter as primary, or moves back to the service role, revisit it with this rule.

**Every column of `tenants`, `tenant_devices` and `devices` is readable by the tenant the row belongs to**, for the same reason: `tenants.geography_notes` (written by staff) and `devices.config` and `openems_component_id` included. A `devices` row is also readable by every former tenant of the meter (`user_is_tenant_of_device` above). Before adding a column to one of those tables, decide whether its tenant, and for `devices` its former tenants, may read it; if not, it goes somewhere else. `src/lib/supabase/__tests__/tenant_access.test.ts` pins the three column lists, so a new column fails it until someone has decided.

Org managers cannot read or write other people's role rows through RLS, so giving, listing and removing tenant access goes through `fn_tenant_access_grant`, `fn_tenant_access_list`, `fn_tenant_access_revoke` and `fn_tenant_access_count`, which are `SECURITY DEFINER` and deal in role-row ids rather than user ids. List, revoke and count are called with the manager's own client and check `user_can_access_microgrid` on the tenant's microgrid. **`fn_tenant_access_grant` is the service role's only**, with the manager passed as `_actor` and checked against the tenant's organization as `user_can_access_org` would check them: the access route finds or creates the account from the address the manager typed, so no signed-in caller can name an account by id (an id a manager can read, such as a `created_by`, would otherwise turn into that person's address through `fn_tenant_access_list`). Do not grant it to `authenticated`, and do not widen the `user_roles` policies to tenant rows instead. The access route is `POST /api/tenants/[id]/access` (community-management, through `composeCommunityManagement`): it finds or creates the account from the address in its body, which is its only field, and answers `201 { access_id, email, email_sent }`; it refuses no account for holding or having held a staff row, and gives no access while the tenant app is off for the unit's organization. `DELETE /api/tenants/[id]/access/[accessId]` calls `fn_tenant_access_revoke` with the manager's own client and answers 204 with no body. The notice that access was given goes through `sendNotice` (the organization's sender, else the deployment's) and never carries a sign-in link or code; the person signs in from the sign-in page. If the routes change shape, update `docs/entity-model.md` § "Decision: tenant access" with them. `tenant_access_accounts` remembers every account that has held a tenant row (a trigger on `user_roles` writes it), so `fn_list_visible_users` keeps former tenants, whose rows are gone, off the Users page too; it has RLS on, no policy and no API grants. `staff_access_accounts` (`20261118140000`) is its counterpart for every account that holds or has held a row whose role is not `tenant`, written the same way and closed the same way. It is history, not who is staff now. `fn_tenant_access_grant` does not read it and checks no staff rows: tenant access does not depend on organization roles, so the grant decides only the actor's authority, the unit and the account. It checks the account under a `FOR NO KEY UPDATE` lock on its `auth.users` row, held to the end of the transaction, so a function that changes the account's role rows and must run one after the grant takes the same lock (the migration's section 4 says more). `fn_list_visible_users` lists anyone holding an org-scoped or `ems_operator` row, and reads the record only for an account that holds no row at all, which it lists if the account was ever staff or never held tenant access. Anyone holding tenant rows and no staff row is left off, whatever they held before. It counts "not tenant" as staff, so if a second role that is not staff is ever added, revisit the listing, the trigger that writes the record and `staffRoles` (`@/lib/auth/access`).

**Do not change what `user_can_access_org` / `user_can_access_microgrid` mean.** Most of the policies chain through them, most of those `FOR ALL`, so read and write move together on each — an error there is a *silent widening*, not a visible failure. The tenant policies and the `supabase_auth_admin` policies on the clients tables do not use them; `SELECT policyname, cmd FROM pg_policies WHERE qual ~ 'user_can_access_(org|microgrid)' OR with_check ~ 'user_can_access_(org|microgrid)'` lists the ones that do. If a capability genuinely differs from org access, add a role value with its own helper, which touches zero existing policies.

**But first ask whether it differs at all.** #316 added `ems_operator` on that reasoning and #321 removed it **the same day** — filed 18:53, merged 22:19, reverted by a ticket opened at 23:16. OpenEMS configuration turned out to *be* org access, and the tell was that the first thing anyone did with the scoped role was grant it org-wide by hand. **Note what #321 did and did not do** — it repointed a *caller* (`fn_microgrids_guard_ems_config`) at `user_can_access_microgrid` and left the helper itself untouched, so no policy moved. Pointing new callers at these helpers is routine; **editing the helpers' bodies is what this rule forbids.**

**Column-level write restrictions are triggers, not policies.** RLS is row-level and column privileges are granted per-role rather than per-user, so neither can express "may update this row, but not these columns". `microgrids.ems_*` is the worked example (`fn_microgrids_guard_ems_config`, most recently re-issued by `20261110142706`, which also makes the four encrypted credential columns service-role writes and keeps each saved credential with the address it was entered for). Three rules for that shape:

- Enumerate the guarded columns **literally**, in both the `BEFORE UPDATE OF <cols>` statement filter and per-column `IS DISTINCT FROM` checks in the body. `UPDATE OF` alone keys off the columns *named* in the statement, not the values, so it rejects no-op resends that ORMs and PATCH handlers routinely produce. No prefix matching and no `information_schema` loops — they silently absorb adjacent columns (the `ems_last_discover_*` health columns must stay writable for Discover).
- **Adding an `ems_*` config column means editing both enumerations, in a new migration.** Omitting it leaves the column writable by anyone who can update the row, with no error and no warning. `src/lib/__tests__/ems-guard-enumeration.test.ts` fails the build when a column on the table is missing from the guard — it reads both lists out of the newest migration that defines the trigger and compares them against the generated types, so neither side is a hand-maintained list.
- **Exempt `service_role` explicitly, and write the structural reason.** It already bypasses RLS and can write these columns; a new trigger exempting it *declines to add* a restriction rather than removing one. Do not write the circumstantial version ("it's the only write path while X") — that expires and reads as an invitation to delete the exemption.

**Rows written only by SECURITY INVOKER functions are guarded by a transaction-local flag that a trigger checks.** `billing_audit_log` is the example (`20261124160000`): `fn_create_billing_period`, `fn_close_billing_period`, `fn_record_line_item_with_audit` and `fn_record_first_line_item_with_audit` insert its rows as the caller, so `authenticated` keeps its INSERT grant and policy, and `trg_billing_audit_log_written_by_functions` refuses an insert by `authenticated` or `anon` unless `mgm.billing_audit_writer` is `'on'`, which each function sets immediately before its INSERT and clears immediately after. Other roles are exempt, as above. `trg_billing_period_transitions_by_close` (`mgm.billing_period_close`, `20261118130000`) has the same shape. `fn_record_line_item_with_audit` and `fn_record_first_line_item_with_audit`, which take the row's actor as arguments, also require a signed-in caller's row to name the caller (`actor_kind = 'human'`, `actor_user_id = auth.uid()`); a non-human actor is recorded through the service role. Since `20261124170000` the same two also require a signed-in caller's manual bill to be entered by the caller (`_entered_by_user_id = auth.uid()`), and build the audit row's details themselves from the bill they write, the bill it replaces (read under lock in the same transaction, for `previous_snapshot`) and the tenant: a caller's `_audit_details` may hold only the keys an app built before that migration sent, which they replace, and anything else is refused (the service role still passes both as given). A new function that writes audit rows sets the flag the same way, and re-issuing one of the four keeps its two lines and, for those two, the actor check and these two rules. This holds only while no function the API roles can execute sets the flag around anything but its own audit insert and PostgREST passes no client-chosen settings through; if either changes, revisit.

**A whole-table restriction on every signed-in user is a table privilege, not a trigger.** `meter_readings` is insert-only for `authenticated` (`20261124120000`): signed-in users, super admins included, select and insert under its `FOR ALL` policy and hold no UPDATE, DELETE or TRUNCATE, so an upsert (`ON CONFLICT DO UPDATE`) from the session client fails too. A device's readings still go with it through `ON DELETE CASCADE`, which runs as the table owner. A feature that corrects a reading gets a `SECURITY DEFINER` function with its own access check and audit row; do not grant UPDATE or DELETE back.

**Two column lists govern `microgrids`, and they have opposite defaults.** The guard above is **deny-by-enumeration**: a column is unprotected until named. `MICROGRID_PUBLIC_COLUMNS` (`src/lib/types/microgrid-columns.ts`) is **allow-by-enumeration**: a column is invisible until named, and the `MicrogridPublic` type beside it must omit the same secrets the constant leaves out. Reasoning from sensitivity gets one of them backwards — "it's a secret, keep it out of the lists" is right for the projection and exactly wrong for the guard. A new sensitive column goes **into** the guard and **out of** the projection.

### Migration conventions — SECURITY DEFINER grants

**Every `SECURITY DEFINER` function MUST `REVOKE EXECUTE FROM PUBLIC, anon` — not just `PUBLIC` — before its explicit `GRANT EXECUTE TO authenticated, service_role`.**

Why both clauses are required: migration `00016_restore_default_grants.sql` historically did `ALTER DEFAULT PRIVILEGES … GRANT ALL ON ROUTINES TO anon, authenticated, service_role`. This was narrowed by `00047` (B2, #270) to remove `ROUTINES` from `anon, authenticated`'s future-grant, but existing functions created between 00016 and 00047 inherited the anon execute grant. `REVOKE EXECUTE FROM PUBLIC` alone does NOT undo that — `anon` is a specific role, not a `PUBLIC` member.

The Supabase linter `anon_security_definer_function_executable` will flag any future SECURITY DEFINER fn that omits the explicit `anon` REVOKE.

Convention applies to all new migrations adding `SECURITY DEFINER` functions:

```sql
CREATE OR REPLACE FUNCTION fn_new(...)
RETURNS ...
LANGUAGE ...
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$ ... $$;

REVOKE EXECUTE ON FUNCTION fn_new(...) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION fn_new(...) TO authenticated, service_role;
```

If the function MUST be anon-callable (rare; typically only public-data RPCs), document the intent in a comment block above the GRANT and skip the REVOKE-from-anon clause.

**PostgREST surface varies by REVOKE pattern.** Test assertions for "anon denied" must accept either of two HTTP shapes — same security outcome, different code:

- **`401 SQLSTATE 42501` ("permission denied for function ...")** — fires when the fn is in PostgREST's schema cache AND anon is denied at the grant layer. Typical for new fns that ship with `REVOKE EXECUTE FROM PUBLIC, anon; GRANT EXECUTE TO authenticated, service_role` (e.g., `fn_list_visible_users` from migration 00046).
- **`404 PGRST202` ("Could not find the function ... in the schema cache")** — fires when EXECUTE is REVOKEd from anon AND PostgREST has refreshed its schema cache to filter the fn out entirely. Typical when a fn is REVOKEd from ALL roles except `service_role` (e.g., the `fn_create_profile_on_auth_user` trigger fn in migration 00047). Also empirically observed for fns that have anon REVOKEd post-creation via `ALTER FUNCTION ... REVOKE` (PostgREST caches at startup; aggressive cache filtering applies).

Regression-test pattern: assert `error.code === "42501" || error.message?.toLowerCase().includes("permission denied") || error.code === "PGRST202"` rather than checking only `42501`. Empirical mapping observed during the Supabase Security wave (B1 #268 / A #269 / B2 #270):

| Migration shape | PostgREST response |
|---|---|
| Pre-existing fn + post-hoc REVOKE FROM anon (B1) | `404 PGRST202` after schema-cache refresh |
| New fn + REVOKE+GRANT in same DDL (A) | `401 42501` |
| Fully REVOKEd (no role retains EXECUTE except service_role) (B2 trigger fn) | `404 PGRST202` |

### Migration conventions — a merged migration is never edited

**Never edit or delete a migration after it merges to `main`; write a new one.** Databases that ran it keep the old version, which is how a production database drifted from the chain (00057 and the pilot overlay were both edited after production ran them). A new migration adds its line to `supabase/migrations.sha256` in the same commit (`shasum -a 256 supabase/migrations/<file> | sed 's#supabase/migrations/##' >> supabase/migrations.sha256`); `src/lib/__tests__/migration-hashes.test.ts` fails otherwise. While a migration's own PR is still open, editing it and its line together is fine.

### Migration conventions — a migration and the tests that assert its objects ship in one commit

**A migration that changes a database object a database-backed test asserts must ship in the same commit as that test and as the regenerated `database.gen.ts`.** Not the commit before, not the commit after.

CI builds its database from `supabase/migrations/*.sql` — `.github/workflows/test.yml` runs `supabase start` and applies the migration files on the PR head. So the migration and the tests are evaluated against each other, and they are red either way round if they disagree:

- Change the test first: it runs against a database that does not yet have the change.
- Change the test after: the PR that adds the migration is red on merge.

This became true in **#324**, which took `SKIP_RLS_TESTS=1` out of the `Test` gate. Before that, the `rls` project never ran in CI, a migration contradicting a database-backed test merged green, and the disagreement surfaced whenever someone next ran the suite by hand.

**The ordering constraint is inside one PR, not across a deploy.** Do not reach for the deploy-ordering framing used for schema changes that must interleave with an app release (`00053`'s header is the worked example of *that* problem) — it names events on the wrong axis for this one and produces a plan nobody can follow.

Worked example: dropping the deprecated `user_can_configure_ems` alias took, in one commit, the migration (`20261114223000`), the alias assertions in `ems_config_access.test.ts`, the regenerated `database.gen.ts`, and the helper-table row in this file.

### Seed migration generation

`supabase/migrations/00003_seed.sql` is **gitignored** and copied by `./setup.sh` from the committed `00003_seed.sql.template`. Its users have no password: MGM signs people in by email link (RFC #186), so locally the link goes to the mail catcher (`docs/setup.md`). Edit the template, never the copy.

## Design System

The shared Tailwind theme lives only in `src/styles/tokens.css`: there is no `tailwind.config.*` and no `@config`. `src/app/globals.css` (loaded on every page) and each interface's stylesheet (`src/gui/<name>/styles.css`, built by `scripts/gui/build-stylesheets.mjs` into `public/gui-styles/`) import it; an interface's stylesheet may add theme variables of its own, such as its breakpoints. `globals.css` generates no classes for `src/gui`, whose classes go into that interface's own stylesheet, and the two stylesheets must not emit the same utility (`src/lib/__tests__/gui-stylesheets.test.ts`). Colour tokens and `--radius` are CSS variables on `:root`, exposed through `@theme inline` (`rounded-sm` to `rounded-xl` derive from `--radius`); fonts, the type scale (rule 3), `rounded-pill`, `shadow-elev-1/2/3` and the default transition are in `@theme`. Spacing is Tailwind's default 4px scale. A class whose value is not defined there generates no CSS and no error, so `src/lib/__tests__/design-tokens.test.ts` compiles `globals.css` and fails instead. `src/app/_dev/components` renders the component gallery.

Surfaces are `surface-1` (cards, panels), `surface-2` (muted areas) and `surface-3` (overlays). `card`, `muted`, `input` and `card-foreground` stay as aliases of `surface-1`, `surface-2`, `border` and `foreground`, so existing classes keep working. `subtle-foreground` is for captions and secondary labels. `energy-solar` (a pale fill; `energy-solar-ink` for solar text and lines), `energy-battery`, `energy-grid`, `energy-load` and `stale` mark energy data only, never status or controls. The dark palette is under `:root[data-theme="dark"]` and the `dark:` variant follows the same attribute, not the operating system's setting. Nothing sets it yet, so dark mode is defined but off; `design-tokens.test.ts` fails if a source file starts setting it or a rule follows the system setting. The same test holds both palettes to WCAG contrast (4.5:1 for text, 3:1 for data marks and the focus ring), and checks text on `primary` and `accent` and the focus ring at every `--brand-hue` in the range the stylesheet calls safe (200 to 340). A colour that fails needs a different value, not a lower bar.

Six rules every contributor must follow:

1. **Status chips:** Use `<Chip>` not raw `<span>` for status indicators. Use `<StatusChip kind="…" status="…">` to map domain enums (billingPeriod, meterType, edge, tenant) — this keeps tone-to-status mapping in one file (`src/lib/gui/status-maps.ts`), which `<StatusChip>` renders and `fmt.status` serves to GUIs. Add new domain enums by extending `STATUS_MAPS` there, not inline.

2. **Format primitives:** Use `<Currency>`, `<Kwh>`, and `<LocalDate>` — never `Intl.NumberFormat` or `toLocaleDateString` directly. Locale comes from `Accept-Language` (detected at the app root); currency comes from microgrid context (wired in `microgrids/[id]/layout.tsx` via `<LocaleProvider currency={microgrid.currency}>`). In-table currency cells use `bareNumber` prop so a figure pasted into a tax return gets `4,216,800` not `UGX 4,216,800`; show currency code only in column headers. Numbers render in Inter's tabular figures (`tabular-nums`, as these primitives do), so columns line up; `font-mono` is for identifiers such as component ids, URLs and token prefixes.

3. **Token classes only:** No Tailwind palette colours (`bg-blue-500`, `text-gray-600`, `text-white`, `bg-black/30`) and no arbitrary colour values (`bg-[#fff]`, `text-[rgb(…)]`, `accent-[color:var(--primary)]`) in `src/app`, `src/components`, `src/lib` or `src/gui`. Use semantic tokens: `bg-card`, `bg-muted`, `text-foreground`, `text-muted-foreground`, `border-border`, `bg-primary`, `text-primary-foreground`, `bg-destructive-muted`, `text-destructive-fg`, `bg-warning-muted`, `text-warning-fg`, `bg-success-muted`, `text-success-fg`, etc., and the token's own utility (`accent-primary`) rather than reaching the token through `var()` (`accent-[color:var(--primary)]`, `bg-[var(--primary)]`, `bg-(--primary)`). `src/lib/__tests__/no-palette-colors.test.ts` enforces this. Font sizes come from the type scale: `text-caption` (12px), `text-dense` (13px, 16px on touch screens), `text-body` (15px, 16px on touch screens), `text-title` (18px), `text-headline` (22px) and `text-kpi` (32px); new text uses one of these rather than an arbitrary size such as `text-[13px]` or a `style={{ fontSize }}`, which `src/lib/__tests__/no-arbitrary-font-size.test.ts` enforces. Tailwind's own sizes (`text-xs`, `text-sm` …) still appear in older code and are not flagged; do not add new ones. On touch screens every text field is at least 16px, so iOS does not zoom into it. A new `--text-*` size in `tokens.css` also goes into `TYPE_SCALE` in `src/lib/utils.ts`, or `cn()` reads it as a colour and drops it; `design-tokens.test.ts` fails until both agree. Gridtop (`src/gui/gridtop`) writes the same classes behind a `gt:` variant that adds no condition (`gt:bg-card`), so its stylesheet never emits a utility `globals.css` also emits; `gui-stylesheets.test.ts` fails when they share one. The variant does rename the classes, so the 44px touch rule in `globals.css`, which finds links by their `flex` or `inline-flex` class, reaches no Gridtop link: each Gridtop link sets its own height on touch screens (`gt:pointer-coarse:min-h-11`, or a fixed size of 44px or more).

4. **Copy table:** Billing figures a person copies are drawn by Gridtop's period-review copy table (`src/gui/gridtop/renderers/period-review`, built-in per-cell copy + keyboard nav, cards on narrow screens), since a GUI package may not import `src/components`. It copies the figures in the `billing.period-review@1` ext (plain numbers: kWh to 3 decimals as the CSV export writes it, and money in the currency's minor unit, which matches the CSV only for a currency with none, such as UGX, since `csv-export.ts` rounds every amount to a whole number; if that rounding changes, revisit), not the text it shows, so a paste gets bare figures with the currency code only in column headers. Grand totals go in a block below the rows, never as a footer row of the table.

5. **Destructive actions:** Use `<ConfirmDialog tone="destructive">` for delete flows (Delete Meter, Delete Tenant). Billing-period close (irreversible) is the contributed `billing.close-period` action, offered on the `billing.close-checklist` view: the host's ceremony step (`ConfirmStep`) shows the ceremony its prepare returns, the same `closeCeremony` the close route sends (#201): the server's totals and warnings, an acknowledgement to tick for each warning that applies (tenants with no bill, bills with no usage: warn-but-allow per #167), and the period's name to type. The confirm sends the review's digest, which `fn_close_billing_period` checks in the same transaction, so never build the totals or acknowledgements on the client. A close refused with `billing_period_totals_changed` is prepared again (its `prepareAgainOn`), so the host shows the new totals. The GUI host takes a step's tone from the action (`actionTone` in `src/lib/gui/host/shared/merge-actions.ts`): danger only for a DELETE or a `risk: "destructive"` action, neutral for every other, typed and ceremony included (ADR-006 decision 10), so the close is drawn neutral — closing is a final commit, not a destruction. Reserve destructive tone for delete flows. Use `<ConfirmDialog tone="neutral">` for non-destructive warnings (e.g. remove-last-tier). Never use `confirm()` — it blocks the main thread and can't be tested.

6. **Picker / empty-state mutual exclusion:** When a list surface has both a switcher control (e.g. a period picker) and an `<EmptyState>`, the switcher MUST NOT render when its underlying collection is empty. The empty-state owns the create CTA at zero; the switcher owns the create CTA at ≥1. Switchers must not include their own internal "no items" empty-state branch — that responsibility belongs to the parent surface, where the canonical first-run pedagogy copy lives. Additionally, when an inline create form is open, the parent's `<EmptyState>` must hide so the form is the sole CTA on screen; the form itself must include a `Cancel` action so the user has an escape hatch back to the empty-state.

## Required Merge Controls

Merge control on `main` is a **maintainer social contract**. GitHub does not block a merge that breaks it: branch-protection or ruleset enforcement is deferred (launch tracker #30 § 2, decided 22 October 2026). The person who merges applies the checklist below and refuses to merge, and asks for a correction, when any item is missing. `docs/operating-model.md` § "Merge controls" and `docs/adr/ADR-002-ci-build-gate-and-merge-controls.md` record the decision.

**Merger checklist.** Before merging a PR to `main`, verify every item:

1. **A pull request.** Nothing is pushed to `main` directly.
2. **`Test`, `CodeQL` and `Build` are green.** `CodeQL` appears as two entries on a PR (the job and the analysis); both must be green. These names are the check names this checklist refers to: rename a job only together with these docs, and do not add a matrix-suffix.
3. **Every commit is Verified.** Cryptographic signature (GPG, SSH, or GitHub's own for web edits); GitHub must show the **Verified** badge on each commit. One-time per-machine setup:
   ```bash
   ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_signing -C "<your-email>"
   git config --global gpg.format ssh
   git config --global user.signingkey ~/.ssh/id_ed25519_signing.pub
   git config --global commit.gpgsign true
   git config --global tag.gpgsign true
   ```
   Then upload `~/.ssh/id_ed25519_signing.pub` at github.com → Settings → SSH and GPG keys → "New SSH key" with **Key type: Signing Key**. After setup, every `git commit` carries an "SSH" signature.
4. **Every commit is signed off.** Each commit ends with `Signed-off-by: Your Name <email>` (`git commit -s`). No automated DCO check reports this today, so the merger reads the commits. Web-editor commits carry the sign-off only if the repository's web sign-off setting is on; check them too. The signature (item 3) and the sign-off are separate: the first is cryptographic, the second a text trailer. A merge commit that only brings in `main` needs no sign-off; `git show --remerge-diff <sha>` prints nothing for one. A merge that resolves conflicts needs `-s`.
5. **Code-owner approval for owned paths.** Areas: database migrations, RLS helpers, roles, the Cordis runtime gate and plugin catalog, the GUI contract and host (`src/lib/gui/`), request middleware, and CI workflows; the exact paths are in `.github/CODEOWNERS`. The approval must be on the **final head commit**, re-requested after any push, and the approver must not be the person who pushed the owned-path change. Reviewers suggest changes rather than pushing to the author's branch. Other changes may be merged by their author once items 1 to 4 hold.
6. **No rebase merging.** GitHub cannot sign the commits a rebase merge creates. Outside contributions are squash-merged; maintainers may merge their own verified, signed-off commits with a merge commit. Squashing does not waive items 3 and 4: they apply to the commits on the PR, including PRs from forks.
7. **Nobody force-pushes or deletes `main`.**

**Check details.**

- **`CodeQL`** — `.github/workflows/codeql.yml` runs `github/codeql-action` on every PR + push to main. The job also gets `security-events: write` to upload results.
- **`Test`** — `.github/workflows/test.yml` runs `npm ci` → `npx tsc --noEmit` → `npm run lint` → `supabase start` → a check that `database.gen.ts` matches the migrations → `npm test` → the 360 px browser smoke (`e2e/`, against `npm run build` and the job's Supabase; timings reported, not enforced) → the fresh-install key check on every PR + push to main, on Node.js 24 from `.nvmrc`. **Since #324 the database-backed suites run in the gate**: `SKIP_RLS_TESTS` is no longer set, the `rls` project executes against a local Supabase started on the runner, and the suites are self-fixturing (no generated seed, no repository secret — `supabase start` produces its own `JWT_SECRET` and `ANON_KEY`). Up to `npm test`, the job takes roughly three and a half to four minutes, of which `supabase start` is ~85s. **No test count is given here on purpose** — it moves with every PR that adds or removes one, and a count in this file would be stale within a day of being written. Read it off the latest `Test` run on `main`. `supabase start` runs with `MGM_ALLOW_DEV_CREDENTIAL_KEY=1`, the development opt-in that lets migration `00018` give the runner's throwaway database a generated credential encryption key; a fresh database without a key or the opt-in stops at `00018` (`docs/runbooks/dek.md`). The fresh-install key check then runs `dek-bootstrap.test.ts` with `RUN_DEK_BOOTSTRAP_TEST=1`: it resets the database without the opt-in, which must fail at `00018`, and then with it. It runs last because it wipes the database.
- **`Build`** — `.github/workflows/build.yml` runs `npm ci` → `npm run build` → the first-load byte-budget check (`scripts/budgets/limits.json`) on Node.js 24 (`.nvmrc`) on every PR + push to main, with no hosting provider, no secrets and no Supabase or application-URL settings, which are read at request time (ADR-003). Do not add a repository secret or a placeholder setting to make it pass; fix the build instead.

**No hosting preview or hosting check runs on a PR.** No hosting provider builds pull requests or posts a status check on them, and none is part of the checklist. The production-build proof is the `Build` job. A merge to `main` deploys nothing: production is deployed separately, by an operator, from a published and verified release asset (`docs/releasing.md`).

**Node.js runtime paths** (each is separate; `.nvmrc` pins 24):
- **Vercel** runs the release asset, whose functions declare the `nodejs24.x` runtime taken from `.nvmrc` (`docs/releasing.md`). `package.json` `engines.node` (`>=24 <25`) agrees with it.
- **Container image** (`Dockerfile`): still `node:20-alpine`. Moving it to Node 24 is a follow-up PR, linked from #33 and covered by the container work in #51; do not change it silently.
- **`Test`**: Node 24 from `.nvmrc`. **`Build`**: Node 24 from `.nvmrc`, with a major-version check.

**For agents you delegate**: every implementer prompt MUST instruct the agent to `git commit -s` AND to commit with the user's existing signing config (no setup work — assume signing is already configured per the one-time setup above; the agent's commit inherits config from `~/.gitconfig`). If the agent's commit doesn't get a "Verified" badge, the user's signing setup needs attention — flag it before pushing. ## Writing Conventions

### A comment asserting a cross-artifact fact must name its own invalidation condition

The failure mode is not staleness in general — it is a comment that states a rule without naming what could change it, so nothing about reading it suggests checking whether it still holds. A docstring stating a permission truth table that a later migration had replaced misled four people during the scoping of #316, precisely because it gave them no reason to distrust it.

Write the version that names what would make it wrong:

> routes through this function rather than `user_directory` because `user_can_see_user_profile` filters `scope_type = 'org'` and would omit microgrid-scoped operators — if that filter changes, revisit

Same length as the version that just states the rule.

**Scope this narrowly.** It earns its keep only for comments asserting a **cross-artifact** fact: a policy enforced somewhere else, or copy that depends on another surface existing. A comment explaining what the code in front of you does needs no invalidation condition — the code is right there and cannot drift from itself. Applied to every comment this becomes "annotate everything", which reviewers stop reading within a sprint.

The reason belongs **in the code**, with the ticket as the long-form record. Nobody reads a ticket six months later while editing a helper.

### A public artifact describing an unfixed weakness is a disclosure regardless of how it is worded

Venue is the decision; redaction is not. Careful wording, omitted identifiers and a neutral tone do not convert a description of an unfixed weakness into something safe to publish — they only make it a quieter disclosure. Decide *where it goes* first.

Applies to issues, PR titles and bodies, commit messages, code comments, and test names in this repo, all of which are public. If the artifact would describe a security weakness whose advisory has not been published yet:

- Put the detail in a **private security advisory** on this repository (Security and quality → Reporting → Advisories → New draft security advisory) and reference the advisory ID here. Reporters outside the team use private vulnerability reporting, which lands in the same place. `SECURITY.md` is the public policy they follow.
- Describe public-repo work by what it *adds* ("microgrid-scoped configuration role"), not by what it *fixes* ("any org manager could read stored cloud credentials"). That includes the fix itself: write its commit messages, code comments, test names, and pull request titles in the advisory's private fork as public text, because the fix's commits reach `main` when it merges, before the advisory is published.
- Develop the fix in the advisory's temporary private fork. GitHub runs no CI or status checks there, and merging from the advisory merges every open pull request in the fork at once. So immediately before merging, the merging maintainer records the commit `main` is at and every pull request's head, merges those heads into it locally, and runs every pull-request workflow job except CodeQL, and the release build checks, by hand on that combined result, in a disposable local environment with synthetic data on a machine they control. Steps that only prepare an Actions runner get local equivalents, and any value a job takes from a secret or its `GITHUB_TOKEN` gets a local, disposable value, never a real secret. They record the tested commits and the results privately, and do not merge if `main` or any head has moved since. They also record that CodeQL could not run in the fork; it runs on `main` after the merge, and they check it and the other workflows on the merge commit before the release is published. Nothing in GitHub blocks the merge (merge control is a maintainer social contract, #30); if enforcement of required checks is added later, it must let repository administrators bypass it, and a bypass used for this merge is recorded privately too. `docs/operating-model.md` § "Security fixes" has the full procedure. Keep the fix in the private fork and on that machine until it merges. Pushing it anywhere else exposes it outside the advisory: a branch on this repo, any other repository (private ones included), CI in any repository, a cloud coding-agent session, or a hosted preview.
- A fix landing on `main` is not the same as a fix being released. Before merging, prepare only the draft release notes and the draft advisory: no version-bump or changelog pull request, pushed tag, built image, or other public artifact exists before the merge. The detail is published once, in the advisory, after the patch release carrying the fix is published and its artifacts are verified usable (before 0.1.0, the next `v0.0.N` pre-release and its deployment asset, `docs/releasing.md`) — artifact before advisory, as `SECURITY.md` sets out. If publishing or verifying the release fails, the advisory stays in draft until the release is repaired and verified again; the merged fix cannot be made private again, so repair promptly. Do not hold the advisory for any installation to upgrade, including installations run by MGM's maintainers: once the fix merges, its diff shows the weakness to anyone who reads it, and the advisory is what tells operators to upgrade. Do not publish it before the release either: an advisory with no installable fix tells attackers where to look and gives operators nothing to install. During 0.x no operator gets advance notice. If that changes — an advance-notice list for operators after 0.x, for example — revise this bullet together with `SECURITY.md`.

## Sensitive Information

**This is a public repo.** Never commit:
- AWS resource names, account IDs, credentials
- Supabase project URLs, keys, or passwords (use `.env.local`, gitignored)
- Business strategy, customer plans and commercial context (the team's private tools hold it). The technical roadmap is public: #30 and #133 live here, and so do RFCs about how MGM should work
- Infrastructure metadata (Terraform state buckets, DynamoDB tables)

When in doubt, ask before committing.
